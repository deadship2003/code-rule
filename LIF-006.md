## LIF-006: Built-in Service Lifecycle CLI [Technical Standard · service lifecycle | Effective 2026-09-07]

> Origin: 2026-09-07 requirement — daemon programs ship a built-in
> lifecycle CLI supporting both user-scope / system-scope systemd service
> management with the full ops subcommand set, automating service unit
> management to reduce hand-maintained deployment scripts. Widened the
> same day to ALL programs, any language (not only Go); the log
> subcommand was ruled non-standard and removed (log investigation uses
> journalctl / tail and other system-native tools); the foreground run
> group returned as a standard top-level subcommand under LIF-005; exit
> codes settled as the two-phase model with service-domain ownership
> (parse errors exit 1 per LIF-005; runtime codes 2/3/4 kept granular
> for ops scripts).

Scope: ALL programs in any IT development project — any language (Go /
C / C++ / Python / Shell etc.). Anything involving daemon / service
lifecycle management (daemon, service subcommand, systemd unit / launchd
plist / Windows service registration) follows this guideline.

### Implementation Rules (Tailscale paradigm, language-agnostic)

Unified entry: `app service <subcmd> [--system|--user] [--json]`
Subcommands: install / uninstall / start / stop / restart / enable /
disable / status (install/uninstall semantics = the service-registration
layer; file-layer artifact deployment belongs to the LIF-008 Makefile
install — the two-layer split is in LIF-008 "install semantic
layering").

1. **Single binary, single entry**: service management is merged into
   the main program (C/C++/Go = single binary; interpreted languages =
   single CLI entry / single package); no hard dependency on
   systemctl/sc existing; platform unsupported → explicit error, never
   pretend success.
2. **Idempotent**: install/start/enable re-run without error; install
   over an existing installation = overwrite and reset the unit
   configuration (no automatic start/enable); uninstall when not
   installed = success message, not an error.
3. **Transient control and persistent auto-start are separate**:
   start/stop/restart touch only the current instance; enable/disable
   change only the auto-start registration and never start/stop
   anything as a side effect.
4. **Three-state scope + strict isolation**: `--system`/`--user` given
   explicitly, default inferred from privileges (root/admin → system).
   `--system` never manipulates user instances; `--user` never modifies
   system units; no implicit cross-scope operations; an unprivileged
   user operating on a system service → explicit error +
   privilege-escalation guidance (sudo/UAC), never silent downgrade.
5. **Unified exit codes, two phases with ownership** (per LIF-005
   rule 6): 0 success / 1 every argv-phase parse error — invalid
   arguments of any kind, globally unified by LIF-005 rule 6 / 2
   insufficient privileges / 3 operation failed (service start failure,
   invalid unit, and other service-operation failures) / 4 platform
   does not support this scope. Codes 2~4 are the runtime business
   codes of this service domain — the command line was legal, the
   execution failed — kept granular as the machine-friendly contract
   for ops scripts ($?-branchable), and used by no other domain:
   ordinary non-service business failures exit 1 per LIF-005 rule 6;
   stderr carries the `error:`-prefixed reason.
6. **Dual output**: all subcommands support `--json`; status carries
   fixed fields: scope / unitPath / installed / enabled / running /
   pid / uptimeSeconds / lastExitCode / lastError / restartCount /
   platformInit.
7. **Leave supervision to init**: the business process does only
   business logic, no self-rolled daemon-fork supervision; the
   crash-restart policy (Restart=on-failure, intervals, retry caps) is
   injected into the unit at install time.
8. **Unit files are generated only by the program**: install generates
   them dynamically; changing configuration = re-install to refresh;
   hand-editing templates is forbidden.
9. **Foreground debug run**: for debugging, run the program itself
   directly in the foreground via the LIF-005 `run` group (`prog run
   --debug`; no service manager involved), with environment variables
   aligned to the unit's runtime environment; the personal-enhancement
   channel is LIF-007 (--debug).

### Universal Red Lines (distilled from incidents, highest priority)

- **Single-instance guard**: every start path (service start / running
  the binary bare, etc.) probes for an existing instance first and
  refuses if one is alive — two instances fighting over a lock/queue =
  random data loss (applies to all single-instance long-poll /
  scheduler processes).
- **Stop-all ordering**: kill detached/nohup processes first, then
  systemctl stop — the reverse order collides with Restart=always and
  resurrects the service into a false-dead state.
- **status source of truth = the init system**; a pidfile is only a
  clue in bare-run mode; both coexisting = abnormal state and must be
  flagged explicitly.
- **Inventory child processes before restart**: a daemon restart kills
  business child processes (in-flight replies/tasks are lost); upgrades
  use a delayed restart (background sleep then restart) or an idle
  window.
