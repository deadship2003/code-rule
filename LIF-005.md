## LIF-005: Unified CLI Syntax and Interaction Standard [Technical Standard · universal CLI | Effective 2026-09-08]

> Origin: 2026-09-08 spec (eight sections, then tightened by four
> follow-up rounds through the same day) — all engineering CLIs (binary
> programs, build scripts) must strictly follow native GNU/POSIX
> industry command-line standards and execute one project-unified
> converged interaction standard: unified subcommand layering, argument
> format, invocation order, and atomic semantics; free dialects and
> non-standard compatibility forms are forbidden. Absorbed along the
> way: the canonical-syntax paradigm, the help/error output policy, the
> two-phase exit-code model with ownership scoping (argv-parse errors
> and ordinary non-service business failures exit 1; codes 2/3/4 are
> exclusive to the LIF-006 service domain), the parse-error
> controlled-exit behavior spec, and the shell/OS exit-code jurisdiction
> boundary. The panoxy CLI is the reference implementation.

Scope: every CLI interaction layer of every IT development project — all
self-developed binaries (panoxy, panicast, telegram-claude-code, …) and
all top-level engineering scripts (build.sh). Goal: one command syntax,
one parameter paradigm, one subcommand layering, one help/error system
across all repositories, eliminating project dialects. Everything stays
within native GNU/POSIX industry-standard syntax — engineering
convergence on top of standard legal syntax, no private non-standard
forms.

### Implementation Rules

1. **Canonical syntax — the only legal form**:
   `prog [--help|--version] <subcmd> [subcmd-opts] [args...]`
   (e.g. `./panoxy service install --system --json`).
   - Pre-subcommand slot: only the two program-level globals `--help` /
     `--version`. Either works bare (`prog --version` prints and exits
     0); bare `prog` with neither global nor subcommand = usage error,
     exit 1.
   - Every business option follows the subcommand; a business option
     before it is an illegal invocation → exit 1.
   - Slot 2+ options: double-dash long form only; valueless booleans or
     key-value strictly space-separated (`--arch all`, `--ver 1.0.0`).
   - Business actions (verbs) live only in the bare-subcommand slot;
     boolean long options must never carry actions (`prog --start`,
     `./build.sh --package` forbidden).
   - Semantic division: subcommands answer "what to do" (verbs: start /
     stop / status); options answer "how" (adverbs: --json, --debug).
   - Also forbidden: custom short options (`-c -d`); subcommand placed
     after options (`prog --debug start`).
2. **Parsing behavior**: scan leading global options; at the first token
   not starting with `-`, stop global parsing — that token is the
   subcommand and ALL remaining arguments go to its parser (recursively:
   a group parser hands off to its action parser). GNU getopt_long argv
   permutation must stay disabled (C: `+` optstring prefix or
   POSIXLY_CORRECT; Go flag stops at the first non-flag natively; shell:
   a manual case loop) — with permutation on, `prog --debug start` would
   be silently accepted and the position rule would be unenforceable.
3. **Binary layering — two-level namespace** (`program <group> <action>
   [options]`) for all resident-service binaries; flat one-level
   command sets are forbidden:
   - `service <action>` — the LIF-006 lifecycle group: install /
     uninstall / start / stop / restart / enable / disable / status,
     each keeping its LIF-006 atomic semantics (install = generate unit
     + daemon-reload, no start/enable; restart = child-process
     inventory + atomic restart; status = systemd truth, supports
     --json).
   - `run` — foreground production run; `run --debug` — foreground
     debug run with LIF-007 environment alignment (scope flags trail as
     options).
4. **build.sh subcommand set** (LIF-008 build.sh contract revised;
   Makefile targets unchanged): `build` (default build → ./bin/) /
   `clean` (clear bin/ artifacts, keep dist/) / `install` (local smooth
   deploy: binary replacement + service restart + health check — an
   upper-layer composite per rule 8) / `package` (multi-arch archives +
   checksums → dist/) / `help`. Invoked per rule 1: `./build.sh build
   --clean --debug`, `./build.sh package --arch all --ver 1.0.0`.
5. **Standard option vocabulary, identical in all programs**: --debug
   (debug mode: symbols kept, no optimization, foreground environment
   aligned) / --clean (full rebuild / cache clear) / --arch (amd64 |
   arm64 | all) / --ver (set the version at packaging time) / --prog
   (binary name) / --json (machine-readable output) / --system / --user
   (systemd scope). Every configurable parameter uses a long option;
   custom short options are forbidden — `-h`, the GNU short alias of
   --help, is the single sanctioned short form (alongside the `help`
   subcommand on build.sh). Disambiguation: `--version` = program-level
   global that prints the program's own version; `--ver` =
   subcommand-slot option that assigns a version at packaging time —
   the slot tells them apart.
6. **Help and error output** (two-phase exit codes with ownership
   scoping: argv-parse errors exit 1; among runtime business failures
   the LIF-006 service domain keeps codes 2/3/4 while every other
   ordinary failure exits 1; stderr content tells the class in every
   case):
   - **Full help, explicit request only**: the complete help (all
     subcommands, all options, descriptions, examples) prints only on
     `prog --help` / `prog <subcmd> --help` (`-h`), to stdout, exit 0 —
     never auto-dumped on an error path.
   - **Syntax errors** (argv parsing fails: unknown subcommand, illegal
     option position, unknown option, missing required argument; exit
     1): stderr = error reason, then a one-line usage synopsis scoped
     to the offending level, then a help pointer. The exit itself is
     controlled and clean — close any opened IO/temp resources, never
     enter any subcommand's business code, no panic, no core dump, no
     stack trace; stdout stays empty (errors never go to stdout, so
     redirection cannot swallow them):

     ```
     error: unknown subcommand "nonexistcmd"
     Usage: prog <subcmd> [SUBCMD-OPTIONS] [ARGS...]
     Use "prog --help" for more information.
     ```

   - **Business errors** (argv legal, execution fails: permission
     denied, connection timeout, resource missing, validation failure):
     stderr = the reason only — no synopsis, no help hint (the command
     line was legal; the problem is the environment or the business,
     not the usage). Exit-code ownership: LIF-006 service-domain
     subcommands return their runtime codes — 2 insufficient privileges
     (the example below exits 2) / 3 operation failed / 4 unsupported
     scope — while every other ordinary business failure exits 1; the
     two exit-1 shapes (usage error vs ordinary failure) are told apart
     by the stderr form, three elements vs reason only:

     ```
     error: failed to open config file /etc/prog/config: permission denied
     ```

   - **Jurisdiction boundary of exit codes**: this contract governs the
     program's own active exit() calls only. Shell/OS-produced statuses
     sit outside it and are exempt — 127 command not found (the program
     never started), 126 not executable, 130 = 128+SIGINT and the other
     128+N signal terminations (the process was killed, it did not
     choose to exit). A panic, assertion failure, or segfault is a bug
     and a crash — never a legal error-handling path; production code
     must not use panic as normal error handling.
   - Every error line carries the `error:` prefix — the stable hook for
     grep / CI filtering; humans get one synopsis line instead of a
     flooded terminal. Precedent: git / go / docker.
   - Incomplete help and silent exits are forbidden; clap / click and
     kin default to dumping full help on parse errors — disable that
     default and install the compact template above.
7. **Verifiability**: unit tests must cover the illegal-invocation
   scenarios (business option before the subcommand, action expressed
   as a flag) and assert the full contract: exit code 1, stderr contains
   the `error:` line plus the one-line Usage synopsis, stdout is empty,
   no full-help dump leaks onto the path, and the process exits cleanly
   (no crash, no core dump); shell completion and help output must match
   the layered subcommand structure.
8. **Semantic red lines (LIF-006 rule 3 restated as global CLI law)**:
   start only starts — never enables; stop only stops — never disables
   and never cleans resources; enable only registers autostart — never
   starts; disable only unregisters — never stops. Composite one-click
   deployment exists only in upper-layer scripts composing the atomic
   subcommands; atomic subcommand semantics are never mutated.
9. **Convergence mandate**: 100% of programs, scripts, and projects use
   this one syntax — action = leading bare subcommand, configuration =
   trailing long options, permanently fixed. The panoxy style is the
   global standard; panicast and all legacy projects are retrofitted to
   it.
